## 現行スプレッドシート

受領URL：https://docs.google.com/spreadsheets/d/1bEbV3bJvGIBhRdKnf3KwBIoJo-2EA-uXRNx2szq6Qx0/edit?gid=2026637461

このgidのCSV exportは認証情報を送らずHTTP 200で取得できた。対象タブは174行・最大34列。C列が担当者／イベント場所のラベル、D列以降が日、担当者行とイベント場所行が上下に並ぶ。B列に枠番号、A列に月見出しがある。管理番号付き店舗名、延長、戻り、不可の入力を確認した。

CSVで分かるのは値のみ。商品名との対応、年、複数タブの役割、色、結合範囲、入力規則、数式・手入力の区別は未確認。月見出しから年を推測して移行しない。CSVだけから予約の開始終了日・総在庫・予備台数を自動確定しない。

閲覧可は書込権限を意味しない。次は原本xlsxの読み取り（色・結合・入力規則確認）または認証済みGoogle接続で構造確認。その後に同期対象セル・商品と枠の対応を確定する。既存の手入力を一括上書きしない。

## 今回の実装（第1段階）

- 管理メニュー「在庫管理表」：PCホバー、クリック・タップ、キーボードで選択。オールマイトとてずくーる!!（準備中）を分離。
- /admin/inventory/allmight は既存Supabase申請の参照のみ。App10、未削除、却下以外を対象とする。
- 初期表示は日本時間の当日から1週間。2週間・1/3/6ヶ月、開始終了日の指定。終了日入力はプリセットより優先。最大366日。
- 商品・申請枠ごとの行に、管理番号、店舗、担当者、利用期間、配送日・集荷日と申請詳細リンクを表示。配送集荷が利用期間外でも期間内なら行を表示する。
- 登録完了・申請待ち・承認済み/連携確認の状態色を分ける。番号だけで登録完了とは判定しない。
- 日付不明・逆転・商品なしの申請は件数を警告し、期間を補完しない。
- 500件ずつ取得し、5,000件超過や取得エラーは不完全な表を出さず停止する。大規模化前にDB側の期間検索が必要。
- 仮押さえ、在庫残数、延長、Sheets同期は未実装。現画面を在庫確約の判断に使わない。

## 次段階の仕様案

1. 在庫マスタ：総在庫数・内予備数を追加。初期値は「未設定」とし、0台と区別。整数かつ0<=予備<=総数。通常利用可能数=総数−予備。オールマイトだけを先行対象とする。ペア商品の台数単位は確認が必要。
2. 仮押さえ：予約ヘッダ（事業・担当者ID・店舗・利用開始終了・状態・作成更新者）と商品明細（商品ID・数量）を分離。通常の仮押さえは利用日で保持し、配送確定後は出庫〜返却・点検完了を在庫拘束期間として管理する案。点検猶予や同日再出庫可否は運用確認が必要。
3. 紐付け：担当者・店舗名・日付近接・商品で候補提示。近接は暫定±7日、日付・商品も補足表示。必ず「なし」を用意。自動確定しない。1申請への二重紐付け・仮押さえと正式引当の二重計上はDBトランザクションと一意制約で防ぐ。承認確定時に再度在庫を検証する。
4. 申請反映：新規・承認・失敗・再試行・編集・削除・復元をすべて対象にする。登録途中でも発行済み番号を保持する。Supabaseを在庫・紐付けの正とし、kintone上での直接変更の取込方針を別途決める。
5. 延長：親申請と延長申請を関連付け、商品数量・料金・承認履歴を保持。自動承認は管理権限と明示操作に限定。現行登録処理は新規納品と配送レコードを作るため、そのまま呼び出さない。旧集荷取消→新納品不要→新集荷設定は失敗・再試行可能な状態管理と監査履歴を用意。APIで集荷不要を確定できるまでは元管理番号の手動変更チェックを残す。空欄送信と配送不要のフィールド仕様を検証してから実装する。
6. Sheets：原本のコピーまたは専用テストタブで差分プレビューを先に作る。予約IDと管理セルの対応、同期キュー・冪等性・リトライ・競合検出を用意。営業の手編集範囲と自動更新範囲を明示的に分離。サービスアカウント等の認証はVercelのサーバー側だけに保存する案。

## 承認が必要な操作

ユーザー指定により、DBマイグレーション適用、本番デプロイ、kintone書込、スプレッドシート上書きは実行直前に内容を提示して承認を得る。提示内容は対象、DDL/変更差分、権限、既存データへの影響、検証結果、復旧方法。コードや未適用SQLの作成・ローカルテストは進めてよい。

次の承認対象は在庫数と仮押さえ保存用DBの追加。物理個体を表す枠か単なる台数枠か、スプレッドシートの商品対応を確認してからDDLを確定する。
