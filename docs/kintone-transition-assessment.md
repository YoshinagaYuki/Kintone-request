# kintone連携の拡張・業務移行の考察

調査日: 2026-10-24。検討資料のみ。kintoneからの新規取り込み機能、双方向同期、代替システム、切替は実装していない。

## 結論

現在のレンタル申請・在庫・配送業務に必要な範囲なら、このシステムへ段階的に移すことは技術的に可能。kintone全体と同じ汎用アプリ作成基盤を再開発するより、実際の業務に絞った管理画面を作る方が適切。現段階でkintoneを停止する判断はできない。

先にkintone直接入力の案件と配送進捗を読み取り連携し、在庫の完全性を確かめながら移行する案を推奨する。現在の旧シート取り込みは在庫予定の移行であり、kintoneレコード全文の移行ではない。

## 現状の根拠

- 既存コードは申請承認後にApp10へ登録し、App50の共有採番を更新し、同じ番号でApp11へ配送情報を転記する。てずくーるはApp49。再試行・延長・通知もこの連携に依存する。
- Supabaseには申請、承認履歴、商品・担当者、在庫、仮押さえ、延長の基盤がある。申請からkintoneへの連携は既に実装済みだが、kintoneで直接作成・変更した全案件を自動で戻す機能はない。
- 取得済みのApp10定義には料金計算、見積・請求の添付、配送・集荷、追跡情報等がある。App11にはDSP側の確認・手配状態、倉庫、最大10枠の機器情報など、現在の申請フォームだけでは置換できない項目がある。
- 採番・配送マッピング・LINE WORKS・メール通知の処理が存在する。外部関係者が使う画面・帳票・通知や、他アプリの採番利用状況までは今回の調査で網羅していない。

参照したローカル実装: `lib/kintone/register-request.ts`、`numbering.ts`、`shipping.ts`、`shipping-mapping.ts`、`lib/inventory/extensions/`、`lib/notify/`。フォーム定義の取得日は2026-10-23（App10 revision248、App11 revision233）。

## まず可能な連携

管理番号に加え「アプリID＋レコードID」を保存して、kintone側の直接入力案件を在庫に反映する。更新版番号と取得日時を持ち、変更・削除・キャンセルを追跡する。商品・数量・利用期間・配送〜集荷の差異を照合画面に出す。番号だけの一致や店舗名の曖昧一致で勝手に上書きしない。

最初はkintoneを案件・配送情報の正とする読み取り連携が安全。双方向編集を導入する場合は、担当者・料金・配送日など項目ごとに編集元を決め、同時編集時に競合を表示する必要がある。Webhookだけに頼らず、定期的な全件照合と失敗時の再実行も必要。

公式APIではレコード、カーソル、コメント、添付ファイル、プロセス管理などを別々に扱う。単純なCSV移行だけで同等のデータと操作性が揃うとは限らない。レコード取得は最大500件、offset最大10,000のため、大量データの取得方式も設計する。[レコード取得](https://kintone.dev/en/docs/kintone/rest-api/records/get-records/)、[API一覧](https://kintone.dev/en/docs/kintone/rest-api/)。

## 業務システムとして置き換える場合の不足

| 領域 | 追加で確認・設計すること |
|---|---|
| 配送運用 | DSP・倉庫の権限、手配済み・不要、追跡番号、配送品目最大枠、例外処理 |
| 金額・帳票 | 計算式と税処理、見積・請求書、ファイル保存・参照、取引先への送付運用 |
| 移行データ | 過去案件、取り消し・削除、添付、コメント、関連アプリ、ルックアップ、元のIDの保持 |
| 権限と履歴 | 社内・外部ごとの項目・案件権限、操作ログ、承認権限、変更前後の記録 |
| 採番 | 共有採番を使う全業務の洗い出し、切替時の競合防止、欠番・再試行、旧番号との対応 |
| 運用 | バックアップからの復旧訓練、監視、失敗キュー、障害時の担当、問い合わせ、更新時の検証 |
| kintone固有機能 | カスタムJS・プラグイン・一覧・帳票・外部連携の棚卸し、APIで移せない履歴の保存方法 |

公式APIがあることは、画面上の全履歴・全プラグイン・全権限をそのまま移せる保証にはならない。添付やコメントはレコード本体と別取得が必要。[REST API概要](https://kintone.dev/en/docs/kintone/rest-api/overview/kintone-rest-api-overview/)。

## 進める場合の順序と切替条件

1. 全アプリ・利用者・外部連携を棚卸しし、データの項目対応を確定する。
2. 読み取り連携で全案件を取り込み、管理番号別・商品別・日別の数量を照合する。
3. 配送・帳票等の不足機能を作り、権限ごとに通常業務と例外業務を検証する。
4. 併用期間中に、新規・変更・延長・キャンセル・請求・返却を実案件で照合する。
5. 件数・日別在庫・金額・添付の一致、復旧テスト、外部関係者の運用確認が完了してから切り替える。切替中の書き込み元は一つに固定する。
6. 旧システムの参照・保管期間と復帰方法を決めてから、別途承認の上で停止する。

費用や期間は、特にDSP・帳票・他アプリの利用範囲が未確定なので現時点では確定できない。ライセンス削減だけでなく、開発・保守・障害対応を含む継続費用で比較する必要がある。
