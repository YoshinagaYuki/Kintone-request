# 仮押さえから申請・承認・kintone本登録（2026-10-28）

仮押さえ編集の登録区分から「本登録（申請情報を入力）」を選ぶと、通常のオールマイト申請フォームへ商品・機器番号・担当者・店舗・日程を引き継ぐ。請求月、取次店、入力者、配送・集荷先等を入力し、最終ボタンで申請を原子的に作成した後、既存 `/api/admin/requests/[id]/approve` を実行する。通常の `registerRequestToKintone` により App10登録、App50採番、App10管理番号更新、App11配送管理、承認履歴・通知を実行する。

- 同じ登録バッチ・追加商品の明示的な紐付けだけを使う。店舗名から推測して別案件をまとめない。
- 通常申請と同じ最大5台。各台の機器番号・背景スクリーン・確保期間を引き継ぐ。未割当は通常承認後の自動割当へ進む。
- 新規RPCは既存の在庫ロック・更新番号を用い、申請、商品ごとの割当、元予定との対応、作成履歴を1トランザクションで保存する。失敗時は部分的な申請を残さない。
- 保存IDと入力ハッシュで再送を識別し、元予定ごとの一意制約でも二重申請を防ぐ。外部連携に失敗した場合は保存済みの同じ申請へ案内し、通常の再実行を使う。
- 元予定・元シートは削除せず、対応する有効申請がある間だけ在庫画面から除外する。申請を削除・差戻しすると元予定が戻る。申請詳細で原文を編集しても対応はDBの紐付け表に残る。
- 無関係な在庫更新は再検証・再試行する。元予定自体が更新された場合は最新の商品・番号・店舗・日程を表示して確認を求め、入力中の申請情報を保持する。
- 配送／集荷の不要は維持し、対象側の必須入力を緩和、kintoneの手配種別は「手配不要」として転記する。通常の顧客申請の既定動作は変えない。

## 検証

- 在庫テスト122件成功、型検査・本番ビルド・差分整合性検査成功。
- ローカルPostgreSQL互換環境で新RPCの2台一括作成、番号維持、同ID再送、重複元予定、在庫競合、古い更新番号、停止管理者、権限を検証。競合時の全件ロールバックも確認。
- 本番DBの検証用2台で一括申請への置換、番号維持、元予定の非重複表示、同ID再送、重複元予定拒否、申請のソフト削除による元予定復帰を確認。顧客案件・kintoneへの書込・採番・通知は行っていない。検証用の申請はソフト削除、仮押さえは取消し、アクティブ件数0を確認。
- 本番ブラウザーで別の検証用2台について、同一案件一覧→本登録選択→申請情報画面の遷移、商品・番号・日程・担当者の引き継ぎを確認。未入力の登録は送信せずエラーになる。390×844で画面幅390、横はみ出しなし、ダイアログx16..374を確認。
- 検証用UI予定の削除・最終デプロイ・モーダル内エラー表示の最終証跡はチェックポイント末尾へ記録する。

実際のkintone新規請求レコードを検証目的だけで作ることは避けた。今回のフォームは独自の採番・外部登録処理を持たず、実運用中の通常承認APIを呼び出す。
